# خطة تنفيذ نظام بدل الراحة — كلية التمريض، جامعة الملك سعود (2027م)

> تجمع هذه الوثيقة دراسة ملفَي الإكسل الحاليين، وتوصيات وكيل الموارد البشرية ووكيل تصميم الويب، في خطة تنفيذ واحدة.

---

## 1. ما يفعله الإكسل اليوم

| الملف | ما يفعله | ما ينقصه |
|---|---|---|
| **آلية حساب ساعات بدل الراحة** | يُسجِّل المهام وساعاتها، ويحسب الأيام المستحقة (كل 7 ساعات = يوم واحد)، ويحفظ الساعات المتبقية | الأيام التي يحسبها لا تصل إلى الرصيد الفعلي |
| **إدارة أيام بدل الراحة** | يعطي كل موظف رصيداً ثابتاً قدره 20 يوماً، ويُسجِّل أيام التمتع (معتمد أو ملغى) مع خطاب توصية بصيغة PDF، ويوفر كشفاً للموظف ولوحة مؤشرات | لا يربط الرصيد بالساعات، ويربط السجلات بالاسم لا بالرقم الوظيفي |

**المشاكل التي يعالجها النظام الجديد:**
- الملفان غير مرتبطين.
- الربط يتم بالاسم، والرقم الوظيفي مُدخَل لـ 4 موظفين فقط من 62.
- أسماء الأقسام مكتوبة بأكثر من صيغة.
- يوجد سجل تمتع مكرر، وسجل بتاريخ خارج سنة 2027.
- لا توجد صلاحيات، ولا مسار اعتماد، ولا سجل تدقيق، ولا إقفال سنوي.

## 2. القرارات المعتمدة (2026-11-17)

| البند | القرار |
|---|---|
| طريقة احتساب الرصيد | مرنة يتحكم بها الأدمن لكل سنة: ثابت أو مكتسب أو مختلط، مع ساعات اليوم والرصيد الأساسي |
| فترة الرصيد | سنوية: لكل سنة رصيدها، ولا يُرحَّل الرصيد إلا بتسوية يعتمدها الأدمن |
| الاعتماد | المدير المباشر (والأدمن احتياطاً) |
| المرفقات | مرنة: إلزامية أو اختيارية لكل سنة، للمهام وللطلبات كلٌّ على حدة |
| الأدوار | موظف، مسؤول، مدير مباشر، متابع (اطلاع فقط)، إضافة إلى مدير النظام |
| إضافة الموظفين | يرفع الأدمن ملف Excel أو يلصق الأسماء والأرقام، فتُنشأ الحسابات ويُسند المنصب لكل موظف |
| الخادم | محلي (SQLite) حتى يُنقل إلى خادم مناسب عبر `HR_DATABASE_URL` |

## 2-أ. الأسئلة الأصلية (للمرجع)

1. **طريقة احتساب الرصيد.** الخيارات:
   - ثابت: 20 يوماً لكل موظف.
   - مكتسب: من الساعات المعتمدة فقط.
   - **مختلط (موصى به):** رصيد افتتاحي + أيام مكتسبة من الساعات − الأيام المعتمدة.

   النظام سيدعم الخيارات الثلاثة عبر إعداد واحد، لكن يجب اعتماد أحدها رسمياً.
2. **ساعات اليوم الواحد.** هل تبقى 7 ساعات دائماً، أم تختلف حسب نوع المهمة (عطلة رسمية أو نهاية أسبوع)؟
3. **مصير الرصيد المتبقي.** هل تنتقل الأيام والساعات المتبقية إلى السنة التالية أم تسقط؟ وما مدة صلاحية اليوم المكتسب؟
4. **مستويات الاعتماد.** هل يكفي اعتماد المدير المباشر، أم يلزم مستوى ثانٍ (الوكيل أو العميد)؟ ومن يعتمد طلبات المدير نفسه؟
5. **خطاب التوصية.** هل هو إلزامي؟ وفي أي مرحلة: مع المهمة، أم مع طلب التمتع، أم مع كليهما؟
6. **الإلغاء المتأخر.** هل يُسمح بإلغاء يوم بعد مرور تاريخه؟
7. **الاستضافة والربط.** هل يُستضاف النظام على خادم داخل الجامعة؟ وهل يُطلب ربطه بالدخول الموحد (SSO) أو بنظام الموارد البشرية؟
8. **استكمال الأرقام الوظيفية.** يجب استكمال الأرقام الناقصة (58 من 62) من الموارد البشرية قبل ترحيل البيانات.

## 3. المعمارية المعتمدة

**لماذا لا تكفي صفحة HTML وحدها:** أي تحقق من الحسابات يجري داخل المتصفح يمكن تجاوزه. لذلك تحتاج الحسابات المتعددة الآمنة إلى خادم.

| الطبقة | الاختيار |
|---|---|
| الخادم | **Python FastAPI** |
| الواجهة | صفحات HTML تُولَّد في الخادم (Jinja2) مع htmx/Alpine.js، دون خطوة بناء ودون SPA، فيسهل على مطوّر واحد صيانتها |
| قاعدة البيانات | **PostgreSQL** (يمكن البدء بـ SQLite)، وتُدار تغييرات البنية بـ Alembic |
| التشغيل | Docker Compose (التطبيق + قاعدة البيانات + Nginx) على خادم Linux داخل الجامعة، مع شهادة TLS |
| التقارير | Excel عبر openpyxl، وPDF عبر WeasyPrint |
| الاختبارات | pytest، وPlaywright، وaxe، وGitHub Actions |

**ما رُفض ولماذا:**
- **Supabase/Firebase:** تُخزَّن فيهما بيانات شخصية لموظفين حكوميين خارج الجامعة، وهذا يتعارض مع نظام حماية البيانات الشخصية ومع ضوابط الهيئة الوطنية للأمن السيبراني.
- **localStorage:** يُستخدم فقط لنموذج العرض في المرحلة 0.

## 5. قواعد العمل

| الرمز | القاعدة |
|---|---|
| BR-01 | الأيام المكتسبة = INT(مجموع الساعات المعتمدة ÷ ساعات اليوم)، والساعات المتبقية = MOD. ساعات اليوم إعداد قابل للتغيير، ولا يُطبَّق تغييره بأثر رجعي. |
| BR-02 | الساعات عدد عشري أكبر من 0، وحدّها الأقصى 12 ساعة لليوم الواحد (إعداد). |
| BR-03 | يُرفض أي تاريخ (مهمة أو تمتع) خارج السنة المالية المفتوحة. ولا يُقبل تاريخ مهمة في المستقبل. |
| BR-04 | يوم التمتع يجب أن يكون يوم عمل: ليس جمعة ولا سبتاً ولا عطلة رسمية مسجلة في تقويم يديره الأدمن. |
| BR-05 | لا يُسمح بطلبين فعّالين للموظف نفسه في التاريخ نفسه، ويُفرض ذلك بقيد فريد في قاعدة البيانات. |
| BR-06 | الرصيد المتاح = الرصيد − المعتمد − المعلّق. يُرفض أي طلب أو اعتماد يتجاوز المتاح، ويتم الفحص داخل معاملة مع قفل السجل لمنع التعارض. |
| BR-07 | إلغاء الطلب قبل تاريخه يعيد اليوم إلى الرصيد. إلغاؤه بعد تاريخه يحتاج اعتماد المدير مع ذكر السبب. لا يُحذف أي سجل حذفاً فعلياً، بل تتغير حالته فقط. |
| BR-08 | السجلات المعتمدة تُقفل. يتم التصحيح بقيد تسوية (+ أو −) مع ذكر السبب، ويحتاج القيد إلى اعتماد. |
| BR-09 | المرفقات بصيغة PDF فقط وبحد أقصى 5MB، وتُحفظ داخل النظام، ولا تُنزَّل إلا بعد التحقق من صلاحية المستخدم. |
| BR-10 | الرصيد يُحسب دائماً من الحركات المسجلة ولا يُكتب يدوياً، باستثناء الرصيد الافتتاحي وقيود التسوية. |

**دورة حياة السجلات:**
- **المهمة:** مسودة ← مُرسلة ← معتمدة أو مرفوضة أو مُعادة للتعديل.
- **طلب يوم الراحة:** بانتظار الاعتماد (يُحجز اليوم مؤقتاً) ← معتمد أو مرفوض ← متمتَّع به (تلقائياً بعد مرور التاريخ) أو ملغى.
- **السنة المالية:** مفتوحة ← قيد الإقفال ← مقفلة.

## 7. الشاشات

**مشتركة لكل الأدوار:** تسجيل الدخول، وتغيير كلمة المرور (إجباري عند أول دخول)، والإشعارات.

### الموظف
- **كشف حسابي:** بطاقات للرصيد الأساسي، والمكتسب، والمتمتع به، والمتبقي، مع شريط تقدّم نحو اليوم التالي.
- **سجلاتي:** مهامي وطلباتي.
- **تقديم طلب يوم راحة:** مع تحقق فوري من الرصيد والتكرار.
- **طباعة الكشف الرسمي.**

### المسؤول (إدخال البيانات)
- **سجل الموظفين:** بحث بالاسم أو بجزء منه أو بالرقم الوظيفي، وتصفية حسب القسم.
- **إدخال الساعات:** شبكة سريعة متعددة الصفوف تشبه الإكسل، مع عمود تحقق يعرض ✓ أو ⚠، واستيراد من ملفات CSV.
- **تسجيل طلب نيابة عن موظف:** مع رفع خطاب التوصية.

### المدير (المتابعة والاعتماد)
- **لوحة المؤشرات:** الإجماليات، ورسم شهري، ومقارنة بين الأقسام، وتنبيهات.
- **صندوق الاعتمادات:** معاينة الـ PDF، واعتماد فردي أو جماعي، وإلزام ذكر سبب الرفض، وعرض الرصيد المتوقع قبل تأكيد القرار.
- **تقويم غياب الفريق.**
- **التقارير:** تصدير بصيغتي Excel وPDF.

### الأدمن
- كل الشاشات السابقة.
- **المستخدمون والأدوار.**
- **الإعدادات:** السنوات المالية والإقفال، وساعات اليوم، وطريقة احتساب الرصيد، والأقسام ودمجها، والعطل الرسمية.
- **سجل التدقيق.**
- **الاستيراد والتصدير والنسخ الاحتياطي.**

### تقارير الإدارة
- الساعات والأيام حسب القسم والشهر.
- الأيام المهددة بالسقوط.
- الطلبات المعلقة ومتوسط زمن الاعتماد.
- نسبة الإلغاء.
- الاستثناءات: تجاوز الرصيد، والتكرار، والتسويات، والسجلات دون مرفق.
- تقرير الإقفال السنوي.

## 8. نظام التصميم

| العنصر | المواصفات |
|---|---|
| اللغة والاتجاه | `lang="ar" dir="rtl"`، مع خصائص CSS منطقية (logical properties) |
| الخط | Cairo (حسب هوية «إتمام»: Bold للعناوين وRegular للنصوص)، مع أرقام بعرض ثابت (tabular-nums) في الجداول |
| الألوان | أزرق مؤسسي داكن (قرابة `#1B3A6B`)، وتركوازي هادئ للتمريض، ومحايدات دافئة، وألوان دلالية للنجاح والتحذير والخطأ. تُعرَّف كلها كمتغيرات CSS (tokens). يُكتب اسم الجهة نصاً، ولا يُستخدم الشعار حتى تعتمده الجامعة |
| الوضع الداكن | يتبع إعداد النظام مع زر تبديل، وتباين لا يقل عن 4.5:1 |
| الجوال | القائمة الجانبية تتحول إلى درج، والجداول إلى بطاقات تحت عرض 640px، وأهداف اللمس لا تقل عن 44px |
| الوصول (WCAG 2.1 AA) | تنقّل كامل بلوحة المفاتيح، وتسمية (label) لكل حقل، وإعلان التحقق عبر `aria-live`، وعدم الاعتماد على اللون وحده لنقل المعنى |
| الطباعة | كشف رسمي بمقاس A4 يضم ترويسة الكلية، ورقماً مرجعياً، وتاريخ الإصدار، وخانات للتوقيع، ورمز QR للتحقق |
| الصياغة | جموع عربية صحيحة: يوم واحد، يومان، من 3 إلى 10 أيام، 11 يوماً فأكثر |

## 9. الأمان والحوكمة

- **المصادقة:**
  - كلمات المرور مُجزأة بـ Argon2id، وطولها 12 حرفاً على الأقل.
  - قفل الحساب بعد 5 محاولات فاشلة، مع تحديد معدّل الطلبات.
  - البنية جاهزة لربط SSO لاحقاً.
- **الجلسات:**
  - ملفات تعريف الارتباط بخصائص `HttpOnly`، و`Secure`، و`SameSite`.
  - انتهاء الجلسة بعد 30 دقيقة خمول.
  - رمز CSRF في كل نموذج.
  - ترويسات CSP وHSTS.
- **الصلاحيات (RBAC):** يُفحص الدور وملكية السجل في كل نقطة وصول بالخادم، ويُكتب اختبار يتوقع رفض الوصول (403) لكل تركيبة من دور وإجراء غير مسموحة.
- **ملفات PDF:**
  - فحص البايتات السحرية `%PDF`، والتخزين باسم UUID خارج مجلد الويب.
  - التنزيل عبر نقطة وصول تتحقق من الصلاحية.
- **النسخ الاحتياطي:**
  - نسخة ليلية مشفرة لقاعدة البيانات والمرفقات.
  - الاحتفاظ بالنسخ اليومية 30 يوماً وبالشهرية 12 شهراً.
  - اختبار استعادة شهري.
- **الخصوصية:**
  - كل مستخدم يرى ما يحتاجه فقط.
  - الاستضافة داخل المملكة أو على خوادم الجامعة.
  - الحسابات تُعطَّل ولا تُحذف، وتُؤرشف السجلات وفق سياسة الاحتفاظ في الجامعة.
- **الإقفال السنوي:**
  1. تنبيه قبل الإقفال بـ 30 يوماً.
  2. تجميد الطلبات الجديدة.
  3. معالجة الطلبات المعلقة.
  4. تطبيق قاعدة الترحيل.
  5. اعتماد تقرير الإقفال.
  6. تحويل السنة إلى قراءة فقط.

## 10. ترحيل البيانات من الإكسل

يُنفَّذ الترحيل بسكربت `import_excel.py` بوضعين: `--dry-run` للتجربة، ثم `--commit` للتنفيذ.

| الحالة في الإكسل | المعالجة |
|---|---|
| الأسماء | تُطبَّع (توحيد الهمزات والتاء المربوطة والمسافات)، ثم تُطابَق بين الملفين، مع مراجعة يدوية للحالات غير المؤكدة |
| الأقسام (نحو 35 صيغة) | قاموس توحيد يراجعه الأدمن، يربط كل صيغة بالقسم المعتمد |
| الأرقام الوظيفية الناقصة | تُستكمل من الموارد البشرية. إن تعذّر ذلك يُعطى الموظف رقماً مؤقتاً `TMP-xxx` ويظهر في تقرير الاستثناءات |
| رصيد الـ 20 يوماً | يُنقل كرصيد افتتاحي بقيد موثّق |
| حالة "معتمد" | تُنقل كـ approved |
| حالة "ملغى" | تُنقل كـ cancelled |
| صفوف مهام فيها اسم فقط | تُستبعد |
| سجل تمتع مكرر | يُعلَّم ملغى مع السبب |
| تاريخ عام 2025 | يُنقل كسجل تاريخي لا يؤثر في الرصيد، أو يُصحَّح بعد إثبات التاريخ الصحيح |

**المخرجات:** تقرير أخطاء بصيغتي Excel وHTML، يذكر لكل صف مصدره (الورقة والسطر) والإجراء المتخذ.

**بعد الإطلاق:** يتيح النظام التصدير إلى Excel بأعمدة الملفات الحالية نفسها، لتسهيل انتقال المستخدمين.
